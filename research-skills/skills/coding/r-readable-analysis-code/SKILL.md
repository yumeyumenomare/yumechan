# 읽을 수 있는 R 분석 코드 작성

## 목적과 범위

- **결과물:** 연구자가 직접 읽고, 지도교수·심사위원에게 각 단계를 설명할 수 있는 R 스크립트. 정확성 다음으로 가독성을 우선한다. 짧고 영리한 코드보다 길어도 단계가 보이는 코드를 택한다.
- **적용:** 연구용 R 스크립트의 신규 작성, 수정, 정리(refactoring), 기존 코드 설명.
- **비적용:** 계량 사양(시차, 최소창, 반복 수, 임계값 방법)의 결정은 `psy-bubble-critical-values`, 엑셀 구조 해석과 변수 구성은 `kb-housing-data-prep`이 맡는다. 이 스킬은 그 사양을 코드로 옮기는 방식만 정한다.

## 프로젝트 구성

분석 프로젝트에 구성이 없으면 다음 배치를 만든다. 이미 구성이 있으면 존중하고, 새 구조로 일괄 이동하지 않는다.

```text
<분석 프로젝트>/
├── <프로젝트명>.Rproj     # RStudio 프로젝트. 작업 디렉토리의 기준
├── config.R               # 모든 사양값·경로·지역 목록 (한 곳)
├── R/
│   ├── 01_load_kb.R
│   ├── 02_build_series.R
│   ├── 03_seasonal_adjust.R
│   ├── 04_test_statistics.R
│   ├── 05_critical_values.R
│   ├── 06_compare_methods.R
│   └── 07_tables_figures.R
├── functions/             # 여러 단계가 함께 쓰는 작은 함수
├── data_raw/              # 원자료. 읽기 전용
└── outputs/               # 단계별 산출물 (.rds, .csv, 그림)
```

- 각 단계 스크립트는 **앞 단계가 `outputs/`에 저장한 파일만** 읽는다. 그래야 단계별로 따로 다시 실행할 수 있다. 부트스트랩처럼 오래 걸리는 단계의 결과는 `.rds`로 저장하고, 다음 단계는 다시 계산하지 않고 그 파일을 읽는다.
- 원자료는 수정하지 않는다. 엑셀에서 손으로 고친 값을 분석에 쓰지 않는다.
- 단계 수와 이름은 작업에 맞게 조정할 수 있다. 번호 순서가 실행 순서라는 규칙만 지킨다.

## 사양값은 config.R 한 곳에

- 시차, 최소창 규칙, 반복 수, 시드, 표본 시작월, 지역 목록, 파일 경로, 계절조정 여부는 `config.R`의 `cfg` 객체에 둔다. 스크립트 안에 사양 숫자를 직접 쓰지 않는다. 예: `lag = 1` 대신 `lag = cfg$lag_main`.
- 새 `config.R`은 [config 양식](assets/config-template.R)에서 시작한다. 값의 근거는 각 사양 스킬 문서에 있다.
- 사양값은 사용자가 명시적으로 요청할 때만 바꾼다. 코드를 고치는 과정에서 사양을 함께 바꾸지 않는다. 바꿨다면 결과 보고 첫 줄에 적는다.

## 스크립트 작성 규칙

새 단계 스크립트는 [스크립트 양식](assets/script-template.R)에서 시작한다.

- **머리말:** 목적, 입력, 출력, 앞 단계, 예상 실행 시간을 파일 맨 위에 쓴다.
- **구간:** `# 1. 데이터 읽기 ----`처럼 끝에 `----`를 붙인 구간 주석을 쓴다. RStudio 개요(outline) 창에 목차로 표시된다. 구간 하나에 처리 하나를 둔다.
- **주석은 "왜"를 쓴다.** 예: `# HLST 와일드 부트스트랩은 시차 항을 넣지 않는다 (원 논문 사양)`. 코드를 소리 내어 읽어주는 주석(`# x에 1을 더한다`)은 쓰지 않는다.
- **이름:** snake_case로 내용이 드러나게 쓴다(`d1_sa`, `cv_mc`, `gsadf_stat`). `df2`, `tmp`, `x1` 같은 이름은 쓰지 않는다. 지역·방법 이름은 `config.R`의 표기와 같게 쓴다.
- **함수:** 한 가지 일만 하고 30줄 안팎으로 유지한다. 필요한 값은 인자로 받고 전역 변수에 기대지 않는다. 함수 바로 위에 하는 일과 반환값을 한두 줄로 적는다.
- **반복:** 지역별 처리 같은 핵심 논리는 미리 만든 `list`에 결과를 담는 `for` 반복문을 써도 된다. 오히려 권장한다. `purrr` 중첩이나 긴 `apply` 한 줄로 압축하지 않는다.
- **파이프:** 기본 파이프 `|>`를 쓰되 한 체인은 4~5단계 이내로 둔다. 더 길면 이름 붙인 중간 객체로 끊고 확인 출력을 넣는다.
- **패키지:** 스크립트 맨 위에서 `library()`로 모두 선언한다. 기본 세트는 `readxl`, `dplyr`, `tidyr`, `ggplot2`, `exuber`, `seasonal`이다. 다른 패키지가 필요하면 이유를 설명하고 추가한다.
- **쓰지 않는 것:** `setwd()`, `rm(list = ls())`, `attach()`, `<<-`, 엑셀 열 번호 하드코딩, 문제를 덮는 `suppressWarnings()`.

## 단계별 검증 출력

- 단계가 끝날 때마다 `stopifnot()`으로 조건을 확인한다: 행 수, 기간, NA 수, 지역 수, 값의 범위. R 4.0 이상에서는 `stopifnot("설명" = 조건)`으로 실패 이유를 붙일 수 있다.
- 실패는 조용히 넘기지 않고 멈춘다. 메시지에는 무엇이 틀렸는지 한글로 쓴다. 예: `stop("D1에 NA가 있는 지역: ", paste(bad, collapse = ", "))`.
- 확인 출력은 짧게 한다. 큰 객체는 `head()`나 요약값만 출력한다.

## 재현성

- 시드는 `cfg$seed`를 각 시뮬레이션 함수의 `seed` 인자로 넘긴다. 전역 `set.seed()` 한 번에 기대지 않는다.
- 실행이 끝나면 `sessionInfo()`와 사용한 `cfg`를 `outputs/`에 저장한다. 예: `writeLines(capture.output(sessionInfo()), file.path(cfg$paths$outputs, "session_info.txt"))`.
- 경로는 프로젝트 루트 기준 상대경로로 쓴다. RStudio 프로젝트를 열고 실행하는 것을 기본으로 한다.

## 사용자에게 코드를 전달할 때

- **새 스크립트:** 구간마다 한두 문장의 한글 설명, 실행 방법, 예상 산출물을 함께 전달한다.
- **수정:** 바뀐 구간만 보여주고 바꾼 이유를 적는다. 사양 변경 여부를 명시한다. 변경이 없으면 "사양 변경 없음"이라고 쓴다.
- **실행 여부:** 실행하지 않은 코드를 실행했다고 말하지 않는다. 사용자가 실행 결과(출력·오류)를 주면 그것을 기준으로 고친다.

## 완료 확인

- 머리말, 구간 주석, 단계 끝의 검증 출력이 있는가?
- 스크립트 안에 사양 숫자가 하드코딩되지 않고 `cfg`를 참조하는가?
- 각 단계가 앞 단계 산출물만으로 실행되는가?
- 쓰지 않는 것 목록의 항목이 없는가?
- 실제로 실행해 확인했는가? 실행하지 못했다면 그 사실과 이유를 보고했는가?
